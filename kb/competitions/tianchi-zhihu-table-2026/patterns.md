## 一、评审偏好（从章程/评分规则可观察到的取向）

- **唯一评分轴是精确匹配通过率**：最终得分 = 正确题数/总题数 × 100，每题独立判分，structure 按 JSON 结构比对、extract/thinking 与原文/标准答案完全匹配（information 页原文）。→ 评审无主观分、无论文/答辩环节，偏好"工程可靠性最大化"而非"方法新颖性"。
- **可自动评分的 Excel/JSON 提交**是硬前提：格式不合规直接无法参与评分。→ 偏好严格遵循输出 schema 的流水线。
- 合规轴（Qwen-only、程序自动生成）为一票否决口径（intro 严禁条款），说明主办方把"云上大模型应用能力"当作隐性评审维度。

## 四、反面观察（常见失分模式，官方规则原文可证）

- **模型来源违规**：使用非阿里云来源模型/第三方闭源 API/本地私有化部署模型 → 结果无效（intro 严禁条款）。对本案最直接的坑：把开源表格识别管线（如自部署 MinerU/VLM）直接搬上赛场。
- **人工介入答案**：人工检查隐藏测试集后手填答案、利用文件名/页码样式/来源网站线索猜答案 → 严禁（intro）。
- **格式失分**：不按 submission.xlsx/JSON schema 生成 → 无法评分（information）。这是自动评分赛最大的非模型性失分源。
- **组队违规**：本赛不允许组队，多人合用账号参赛存在违规风险（intro"不允许多人组队"口径推论，具体判罚规则未公布——推论标注）。

## 五、赛点检查表（评审标准 → 可执行检查项）

- [ ] 提交生成全链路跑在 Qwen（百炼 API/PAI）上，无任何其他模型调用痕迹（含 embedding/OCR 组件来源核查）
- [ ] submission.xlsx 两列 schema 逐行自检：id 覆盖 tests.xlsx 全集、structure 题 JSON 可被标准解析器解析、空值用空字符串
- [ ] structure 题输出前做 JSON schema 校验（row/col 索引范围、row_span/col_span 正整数、text 非空单元格完整性）
- [ ] extract 题答案与原文逐字符对齐（不归一化大小写/全半角，除非 answer_format 明示）
- [ ] thinking 题做数值二次校验（重算+格式按 answer_format 归一）
- [ ] 不可答题置空字符串而非省略行
- [ ] 全流程脚本化可复跑（应对官方"待定"的每日提交次数/成本上限约束）

## 六、对本框架的启示（喂给 K-02 / 验收报告）

- 方向契合：文档智能/多模态表格理解，与既有 MinerU 文档解析线条方法论重叠度高；但**实现栈必须整体迁移到 Qwen+阿里云云产品**，迁移成本是参赛的主要工程量。
- 个人赛 + 程序自动评分 → 适合单人快循环交付；季度赛季制意味着**失败成本低**（错过一个季度可下季度再来），适合作为管线迭代试验场。
- 评分是全有全无的逐题匹配 → 管线设计应优先保 structure/extract 题的高确定性收益，thinking 题用校验器兜底，而非追求端到端大模型一次成型。
- 合规栈：答案程序自动生成留痕（脚本+调用日志）即满足"非人工填写"举证要求。
