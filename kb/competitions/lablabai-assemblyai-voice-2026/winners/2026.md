## 二、深构条目（每席四节）

> 亮点按本赛评审四维归类：Application of Technology / Presentation / Business Value / Originality（来源[12]）。"骨架"= 技术方案主线（代码型作品）。

### Concierge（Winner，SoloRobot，1 人队）

**方案骨架**（来源[2]）：
1. 入口即普通电话：宾客拨前台免安装；话务交换机已携带房间号上下文注入代理，免身份询问。
2. AssemblyAI Voice Agent API **单实时会话**承载全对话：语音识别、按嘈杂房间调优的 turn detection、keyterm prompting 锚定房号/菜名、barge-in 打断、client-side tools 直连机器人实时状态；LLM 自选（经 OpenRouter）。
3. 工具化履约：点 amenities/餐饮（对照实时菜单与库存，缺货自动给替代）、把桌面待发的外卖订单并进同一机器人行程、FAQ 精确数值应答（退房时间/延迟退房费/设施时间/WiFi/停车/洗衣）、按房号追踪订单实时 ETA/途中改单/召回机器人。
4. 分诊升级：需人工的事项（延迟退房/丢房卡/空调故障/投诉）转前台队列后礼貌挂断。
5. 物理闭环：每个请求映射为 MuJoCo 仿真中的真实派送任务（转向柜台装载→行驶走廊→振铃房间电话→开舱→归位停靠）；ops dashboard 实时呈现通话/机队/订单/升级/库存，web demo 在浏览器内同时跑语音与物理仿真。

**亮点**：
- （Application of Technology）单会话内组合 SR + turn detection + keyterm + barge-in + client tools 五项能力，不换连接不转接，会话完整性作为卖点表述（来源[2]）。
- （Originality）5 席中唯一"语音→物理执行"闭环：语音层接机器人派送（MuJoCo 仿真），把 Voice Agent 从对话工具升维为履约入口（来源[2]）。
- （Business Value）酒店前台痛点高频且具体（"One phone call, one robot at your door"）；"physical AI voice layer, starting with hotels"给出可扩展的行业序列叙事（来源[2]）。
- （Presentation）live demo（Vercel）语音+物理浏览器内并行可视，社区热度 5 席最高（likes 11，社区积分榜居首 1,175 分，来源[1][2][11]）。

**不足与可改进点**：
- **公开仓库已撤**：提交契约要求的公开 GitHub 仓库（repoLink）赛后 404（用户存在、25 个公开仓库无此仓库——转私/删除，来源[11]），可复现性与"声明-实现一致性"核对断档（核对维度：开源可复现/交付契约赛后状态）。
- "物理 AI"的执行层是 **MuJoCo 仿真而非真机**，仿真-现实差距未量化披露（核对维度：声称与实测）。
- 多语言能力（"English, Mandarin or a mix"）无实测数据；证据密度显著低于 ClauseCatcher/Beacon 两席（无测试数/延迟/准确率披露）（核对维度：量化验证）。
- 本席 flight 载荷无评委评语块，评审视角短板不可直证（见数据缺口）。

**可迁移性**：
- "电话即前端"免安装入口 + 交换机元数据免身份询问——任何 to-C 履约场景（物业/诊所/外卖）可直接套用，复用成本低（单 Voice Agent 会话）。
- "语音层 + 执行层 + ops dashboard"三层结构是把语音代理接到既有执行系统的通用参考架构（执行层不必是机器人）。
- keyterm prompting 锚定领域实体（房号/菜名）是领域语音代理标配技巧，即取即用。
- 风险提示：物理执行叙事若无法配真机/仿真证据，评审可证伪——我方借鉴时优先补"执行证据"位。

### ClauseCatcher（Winner，ClauseCatcher，1 人队）

**方案骨架**（来源[3][7]）：
1. 合同上传：pdfplumber 解析 PDF 逐条抽出条款，原文一次性保存为唯一"可说文本源"。
2. 监听：浏览器麦克风 PCM16 → WebSocket → FastAPI → AssemblyAI Streaming STT v3 全程转写，STT 会话以合同条款播种 keyterms（作者自注：机制已接线但增益未测量）。
3. 核查：每个 finalize 句送 Gemini（gemini-3.5-flash-lite）对照条款，**只返回 verdict + clause ID，永不生成文本**；核查失败/超时一律归"unclear"，不归矛盾。
4. 提醒：矛盾触发 AssemblyAI Voice Agent `reply.create` + say_exactly 指令**逐字朗读原条款**，浏览器 cockpit 同步警示卡；服务端事后比对朗读转写与原文（相似度 1.0 才记 literal_spoken）。
5. 应答：经理从条款栏选号，服务端直查条款同样逐字读回（刻意绕开 tool-calling——该路径实测不可靠）。
6. 报告：会话结束输出条款引用/矛盾清单/通话统计。

**亮点**：
- （Application of Technology）**双 AssemblyAI 连接的分工架构**（有 ADR-0001 存档）：Streaming STT 只听不答（单 Voice Agent companion 模式实测会抢话，被否决），Voice Agent 只说不听（say_exactly 是逐字校验能通过的前提，有 A/B 实测）——两 API 各用其长且决策留痕（来源[7]）。
- （Application of Technology/Presentation）**量化验证文化为 5 席之最**：14/14 矛盾捕获、0 误报（32 句标注集）、median 3.5s、警报落地 4-6.5s（五次 live 记录）、逐字相似度 1.0、$0.08-0.15/通话成本、151 后端 + 42 前端测试全过，原始日志入库 `docs/evidence/` 供免复现查验（来源[7]）。
- （Originality/Business Value）高保真铁律"LLM 只做选择不做措辞，说出的每个字来自合同原文"+ 失败归"unclear"不指控 + 警示需证据（clause ID）+ 20s 限频——合规场景的安全设计三件套（来源[3][7]）。
- **评委评语直证**（来源[3] flight 载荷）："An excellent and highly differentiated application…"；架构（STT 连续监听 + Gemini 受限核查 + Voice Agent 只念原文）与验证（约 5 秒端到端、14/14、151 测试、$0.08-0.15）被逐项点名，评"one of the stronger submissions technically and conceptually"。

**不足与可改进点**：
- **评委明示短板**：准确性与付费意愿未在真实销售/合规团队验证（评语原文"validating accuracy and willingness-to-pay with real sales and compliance teams"；README 自标市场假设 "$30-60 per-seat hypothesis (untested with buyers)"）（来源[3][7]）。
- claim-check 准确率在**自建 4 条款 fixture** 的 32 句上测得，未在未见过的合同上测（README 自认）——泛化性未证（来源[7]）。
- keyterms 播种增益未测量（README 自认"mechanism, not a result"）；物理麦克风未测（Chromium 假设备）（来源[7]）。
- 产品边界：不接入呼叫平台、不注入通话音频，提醒只在自家浏览器页出声——演示友好但现场采用价值打折（来源[7]）。

**可迁移性**：
- "生成式组件只做选择/判断、措辞一律取自权威原文"是法律/医疗/金融等高保真语音场景的通用铁律，作为模式复用成本极低。
- "STT-only 听 + Voice Agent-only 说"的双连接分工是所有边听边说场景的踩坑结论，可直接省去同类实测成本。
- say_exactly 指令 + 事后相似度校验的逐字闭环，适用于任何"语音回读原文"合规位。
- 证据文化（日志入库 + ADR + 单次运行如实标注）可整体映射到我方作品的可验证性包装，成本低。

### Muninn: Living Memory System for Technical Work（Winner，High Entropy，1 人队）

**方案骨架**（来源[4][8]）：
1. opt-in 捕获：显式开启会话（24kHz AudioWorklet PCM16 流或 1-tap 语音便签）；双运行模式——Co-Pilot（双向对话、VAD 打断、口头反馈）与 Scribe（静默缓冲多说话人会议）。
2. 提取：边缘编排管线把语音切成**原子可验证主张（claims）**，五分类（observation/hypothesis/decision/task/question），每条带来源会话/说话人/置信级/逐轮时间戳；实体（project/component/person/vendor）与关系边（blocks/depends_on/resolves）同抽；敏感标记分流。
3. 图谱：Neon Serverless PostgreSQL + pgvector 存关系型知识图谱，递归 CTE 解多级依赖链。
4. 主动推理：后台引擎持续审计开放回路/已解锁任务/冲突决策，自主触发 resurfacing 告警。
5. 隐私双架构：web 端 sessionStorage 临时沙箱（关页即焚 + 可选云同步）、Android 本地优先持久化；Sensitivity Review Gate 隔离凭证/财务/_off-record 内容，默认丢弃。
6. 栈：Next.js 15（Cloudflare Pages）+ Hono（Cloudflare Workers）零冷启动 + AssemblyAI + Capacitor Android APK；MIT。

**亮点**：
- （Application of Technology）同一 API 的两种会话形态产品化（Co-Pilot 对话式 vs Scribe 记录式，按会议语境选择）；零冷启动边缘栈（Workers + Neon serverless）作为语音后端工程选项（来源[8]）。
- （Originality）问题定义差异化："工程遗忘症"——不是会议摘要而是**工程记忆系统**；主动重现（开放回路/冲突决策审计）从被动记录升到主动提醒（来源[4][8]）。
- （Application of Technology）数据模型深度：五类原子主张 + 全套溯源字段（来源会话/说话人/置信/逐轮时间戳）+ 关系边——记忆可验证而非口述转储（来源[8]）。
- （Presentation）单人队交付广度罕见：Web + Edge API + Android APK + Google Slides pitch deck + SECURITY/PRIVACY 政策 + MIT（来源[8]）。

**不足与可改进点**：
- **量化验证证据缺位**：README 全文无测试数/准确率/延迟实测（对照 ClauseCatcher 151 tests、Beacon 420 tests，本席证据密度 5 席最弱）（核对维度：量化验证；来源[8]）。
- 核心环节未证：claims 抽取的分类准确率/召回率无测量，"可验证主张"的可靠性依赖未测的 LLM 步骤（核对维度：核心管线验证）。
