# TSFM 上边缘：把"零样本预测模型"当在线系统用，会撞上什么

> 来源：https://arxiv.org/abs/2611.30404 （2026-11-23，摘要经 arXiv API 实抓 2026-11-25）。无官方代码仓（GitHub search 2026-11-25 实查）。本卡内容出自本次抓取的摘要，未读 PDF 全文。

## 是什么

一项**系统口径的实证研究**（Marco Pichler 等）：TSFM 要在边缘设备上当预测系统用，必须随新观测**增量刷新**预测，且隐私/延迟要求常把刷新逼到资源受限的端侧。作者提出三个硬要求——**刷新快、延迟与峰值内存有界（不随流增长）、历史累积下精度保持**——并逐一归因到结构性质：非因果模型每次更新都全量重算；因果注意力可用 KV cache 但缓存随保留历史**线性增长**；因果递归模型以**固定尺寸状态常数时间更新**。论文把各模型的状态跨刷新持久化后实测：**9 个配置**在 GPU + 3 种边缘设备上跑，结论——没有任何模型在训练上下文之外平均保住精度，**多数在远未到上下文上限时就开始丢**；KV cache 让延迟与内存随保留历史线性上涨。**TiRex-2 是 9 配置中唯一三项全达标**的：GPU 14ms / Raspberry Pi 5 120ms 刷新，百万步延迟、能耗、峰值内存恒定，且在无截断历史上保持精度。

## 解决什么问题

TSFM 的论文口径是"单次预测精度"，部署口径是"流式服务"——两者之间的鸿沟没人系统量化：刷新一次多少钱、状态能不能跨刷新复用、历史越攒越长之后还准不准。这篇把**因果性→状态持久化→资源边界→精度保持**串成一条可测的链，给出首个跨模型跨设备的对照数据。

## 相比前方法优势

- **系统三要求框架**：刷新速度/资源有界/精度保持的三角把"能不能部署"从感觉变成可检查清单；
- **架构性质→部署后果的显式映射**：非因果（全量重算）vs 因果注意力（KV 线性涨）vs 因果递归（常数状态）的权衡讲清了"为什么递归结构在边缘吃香"；
- **跨设备实测**：GPU + 3 边缘设备（含 RPi5）的资源数字可直接引用，不是纸面估算；
- **反直觉发现**：上下文大 ≠ 流得久——多数模型在上下文上限之前就丢精度，这对"长上下文模型可以无限滚动"的直觉是直接纠偏。

## 局限（如实标注）

- 无官方代码仓（GitHub search 2026-11-25 实查），测试 harness 不可直接复用；
- 覆盖 9 配置（摘要未列全名单），TSFM 生态里新模型需要重新按此口径自测；
- "精度在上下文外退化"的机理（漂移 vs 位置编码外推失败 vs 状态饱和）摘要未展开；
- 结论依赖各模型自身训练数据分布与被测流匹配度，跨域流的退化曲线可能不同。

## 如何用于比赛（比赛映射展开）

- **数模-预测与评估**（reuse_cost 低）：赛题若含"持续监测+滚动预测"场景（电力负荷、水质、交通流），用三要求清单做部署方案论证；"多数模型远早于上下文上限就丢精度"是现成的风险分析素材——支持"定期重校准/重训"的设计决策，而不是"一次训练终身使用"。
- **黑客松-数据与算法**（reuse_cost 中）：48 小时做端侧预测 demo 时，按"递归结构+固定状态"优先选型（摘要口径 TiRex-2 全达标、RPi5 120ms），避开 KV cache 线性增长的注意力模型；把三要求做成 demo 的验收指标，评审时可直接对照。
