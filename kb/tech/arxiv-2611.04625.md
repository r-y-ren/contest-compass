# QueryFlow：查询条件也要跟着图上下文一起演化

> 来源：https://arxiv.org/abs/2611.04625 （v1 2026-11-03，摘要经 arXiv API 实查；GitHub search 2026-11-13 实查无官方实现）。本卡内容出自本次抓取的摘要，未读 PDF 全文。

## 是什么

多跳 RAG 检索器。问题设定：有限检索预算下找回跨页互补证据；对原问题独立打分会漏掉"相关性要经中间事实才显形"的支持单元。已有两条路——迭代检索（把中间事实写进后续查询）与图检索（显式建模证据单元间关系）——但固定查询的图检索器只更新实体表示，**查询条件本身不随累积的关系上下文调整**。QueryFlow 把多跳证据恢复形式化为"证据表示与查询条件的耦合演化"：用共享查询状态**递归整合图上下文的查询条件化摘要**，该状态进而控制后续传播的边界输入（boundary inputs）与关系特征。官方口径：四个代表性多跳 QA 数据集上，macro **Recall@10 +4.98、Full Recall@10 +8.40、LLM-Acc +8.0 个百分点**。

## 解决什么问题

"拿着原问题一路打分"在多跳场景的结构性缺陷：第二跳的证据与原问题字面相关性低，独立打分天然漏检。QueryFlow 让"要找什么"本身随"已找到什么"演化——查询状态是第一类公民，不是固定的外部常量。

## 相比前方法优势

- **查询状态演化机制**：相对迭代检索的文本级 query rewrite，条件化摘要进共享状态是表示层的演化，梯度可训；相对固定查询图检索器，查询侧不再僵死；
- **三指标齐涨**：召回（R@10）、全召回（FR@10，要求答案全部支持单元都被找回）、端到端 LLM-Acc 同步提升，说明增益从检索层传导到了生成层；
- **预算友好**：机制目标就是"有限预算内补回隐藏相关单元"，与赛题/生产常见的检索次数限额对齐。

## 局限（如实标注）

- **无官方代码**：GitHub search 无实现仓，复刻要自建（共享查询状态的注入方式、边界输入控制的细节需读全文）；
- 增益为论文自报，四个数据集都是多跳 QA（HotpotQA/MuSiQue 类），单跳/长文档场景未测；
- 递归更新引入的推理开销与延迟数字摘要未给，预算敏感场景要实测；
- "查询条件化摘要"依赖摘要器质量，摘要误差的误差传播未分析。

## 如何用于比赛（比赛映射展开）

- **黑客松-数据与算法**（reuse_cost 中）：多跳 QA/证据核查题的检索器设计模式——即使不用图，"维护一个随检索结果递归更新的查询状态、用它改写下一轮检索的边界条件"这个模式在任何检索栈上都能落；有图时按论文的"条件化摘要→共享状态→控制传播"三层复刻。答辩时的差异化点：你的检索器知道"自己已经知道了什么"，而不是每次都从头看原问题。

**族内定位**：GraphRAG 线已有 PonsRAG（长叙事桥接）、SelfGraphRAG（合成监督）；同批 ArcRAG（本批姊妹卡）占"跨构建可移植"位。QueryFlow 占"**单构建内检索质量：查询-证据耦合演化**"位——ArcRAG 答"换构建还稳不稳"，QueryFlow 答"同一个构建里怎么把隐藏支持单元捞回来"，前者重工程自由度、后者重召回上限，按赛题瓶颈选。
