# ReTrace：SOP 跑千遍何必每步问 LLM——把 agent 的"为什么这么走"蒸馏成代码选步的工作流

> 来源：https://arxiv.org/abs/2611.14492 （v1 2026-11-10，摘要经 arXiv API 实抓）；GitHub search 无官方实现（2026-11-19 实查）。本卡内容出自本次抓取的摘要，未读 PDF 全文。

## 是什么

**SOP→工作流的编译框架**。场景：业务流程自动化里同一 SOP 反复在新输入上执行，LLM agent 能照 SOP 办事，但每步每跑都要调一次 LLM 选动作，规模化后延迟与成本难堪。ReTrace 的关键洞察：agent 每次工具调用附带的**推理文本**（它自己写的"为什么这么做"）藏着步进条件——而工具调用序列本身不含。管线：从少量带日志的 agent 运行中**抽取每步条件** → 跨运行**合并成紧凑规则文档** → 从规则文档**生成可执行工作流**（由代码而非 LLM 选下一步）。只有最后编译步依赖编排平台，规则文档可为不同平台重编译。官方口径：生产平台 79 流程完成率 93.8%（agent 96.8%）但单任务成本 -24%；τ²-Bench 75.8% 对 80.6%，1.3s 对 170s；对训练失败的修复三轮把 k=2 工作流从 66.7% 提到 81.2%；SOP-Bench 上经修复 87.8% 对 agent 85.5%。

## 解决什么问题

"每步都问 LLM"的 agent 在重复性 SOP 场景里为灵活性付出不必要的税。ReTrace 把灵活性的一次性投入（收集带推理文本的轨迹）转化为确定性的执行资产（工作流），运行时零 LLM 选步——是 agent 蒸馏线（库内 2611.14492 之前无此形态卡）里"轨迹→规则文档→平台编译"的中间表示路线。

## 相比前方法优势

- **条件来源是推理文本不是调用序列**：工具调用对不含分支条件，agent 自述的"为什么"才是规则的原料——这一手让规则文档可读、可审、可人工改；
- **中间表示可移植**：规则文档与编排平台解耦，换平台只重编译最后一层；
- **修复闭环**：训练失败案例反哺工作流修复，有明确迭代数字（66.7%→81.2%）；
- **生产级证据**：79 个真实流程+成本延迟双降，不是纯学术基准。

## 局限（如实标注）

- 无官方实现（2026-11-19 GitHub search 实查），"抽取条件"的具体提示词与合并算法需自行摸索；
- 前提是任务有稳定 SOP——探索型/开放型任务没有可编译的固定结构；
- τ²-Bench 上让 4.8 个点：变化频繁、分支爆炸的流程里规则文档会退化为不可维护的大 caseload；
- 生产平台数据来自作者自有平台，外部流程（如 ITSM/工单类）的可迁移性未测。

## 如何用于比赛（比赛映射展开）

- **双创-文书与申报**（reuse_cost 中）：SOP 驱动流程自动化项目的核心叙事模板："演示阶段用 agent（灵活），交付阶段编译成 workflow（便宜快稳）"，配合 93.8%/96.8%、-24% 成本、130 倍延迟三组对标数字与"规则文档可跨平台编译"的架构图。
- **黑客松-数据与算法**（reuse_cost 中）：限时/计费 agent 赛的双阶段打法——先 agent 探路攒轨迹，后编译工作流跑成绩；若赛制重完成率不重速度，则用修复闭环持续涨点（81.2% 路径）。
